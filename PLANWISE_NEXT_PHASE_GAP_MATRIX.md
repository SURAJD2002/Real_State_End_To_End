## Epistemic Status Classifications
- **`IMPLEMENTED`**: Fully functional, verified in codebase, backed by passing automated tests.
- **`PARTIAL`**: Architectural foundation or component exists, but key production or statutory capabilities are incomplete.
- **`MISSING`**: No active implementation exists in the current codebase (research claims it is missing, and audit confirms).
- **`PROPOSED`**: Conceptualized in research or design documents, but not yet engineered.
- **`BLOCKED`**: Contingent upon upstream statutory, legal, or architectural prerequisites.
- **`UNKNOWN`**: Indeterminate or unverified without external authority access.

## Key Audit Revelations: Actual Repo vs. Research Claims
1. **L0–L4 Site Confidence**: Research claimed this was missing. **Fact:** `workers/evidence/evidence_engine.py` and `packages/schemas/site_evidence.py` already implement complete L0–L4 tiering.
2. **PostGIS Schema**: Research claimed parcel storage was planar JSON without PostGIS. **Fact:** `database/migrations/01_init_postgis_schema.sql` creates PostGIS extension, geometry columns (`boundary_wgs84`, `boundary_projected`), and GIST spatial indices.
3. **Multi-Jurisdiction Rules**: Research claimed only hardcoded Mumbai rules existed. **Fact:** `packages/rules/bbmp_bengaluru_2026.json` and `packages/rules/golden_benchmarks.json` already exist in declarative JSON format.
4. **Construction Scheduling**: Research claimed scheduling was completely unmodeled. **Fact:** `workers/schedule/cpm_engine.py` exists with a 15-activity precedence network and BUA-scaling logic.
5. **IFC Implementation**: Research claimed IfcOpenShell is used. **Fact:** Planwise uses a native, zero-dependency STEP physical file serializer in `manifest_engine.py`, which is faster but currently lacks standard georeferencing (`IfcMapConversion`) and standard property sets (`Pset_*`).
